# Архитектурные решения — интеграция API каталога

> Решения, которые повлияют на дизайн модуля. Каждый компромисс документирован: какие были варианты, что выбрали и почему. Это для будущей команды (и нас через полгода) — чтобы не пересматривать каждое решение заново.

## A1. Структура модуля `src/api/`

**Options.**
- A. Один файл `src/api/catalog.js` со всей логикой: HTTP-клиент, повторы, кеш, адаптер.
- B. Разделение по ответственности: `catalog.js` (HTTP + повторы), `catalog-adapter.js` (преобразование в доменную модель), `errors.js` (типы ошибок), `mocks/catalog.json` (фикстура).

**Decision.** Вариант B.

**Rationale.** В одном файле всё уместится, но мы целимся в переиспользование адаптера (для `checkout`, `wishlist`) и единый `ApiError` через весь API-слой. Разделение оправдывает себя на следующем эндпоинте.

## A2. Источник данных и переключатель

**Options.**
- A. Все запросы всегда идут в API. Моки только для модульных тестов.
- B. Флаг `VITE_USE_MOCK_DATA=true` в `.env` переключает между API и `src/api/mocks/catalog.json`. По умолчанию `true` в режиме разработки.
- C. Vite-плагин для перехвата моков.

**Decision.** Вариант B.

**Rationale.** Интеграция должна работать без подключения к реальному поставщику. Простой `.env`-флаг прозрачен и не требует дополнительных зависимостей. Плагин — избыточно.

## A3. Retry и таймаут

**Options.**
- A. Без повторов, без таймаута — пусть `fetch` падает.
- B. `AbortController` + повтор до 3 раз с нарастающей задержкой (1с / 2с / 4с).
- C. Сторонняя библиотека (`axios-retry`, `ky`).

**Decision.** Вариант B.

**Rationale.** Минимум зависимостей. `AbortController` — стандартный API. Повтор на `NETWORK`, `TIMEOUT`, `SERVER`; для 4xx ошибок повтор не делаем (баг конфигурации не починится повтором).

## A4. Кеширование и фолбэк

**Options.**
- A. Без кеша. При сбое API — пустой каталог.
- B. Кеш в `localStorage` под ключом `products_cache` с меткой времени. При сбое — отдаём кеш с пометкой «возможно неактуально».
- C. Service Worker для офлайн-режима.

**Decision.** Вариант B.

**Rationale.** Service Worker — отдельный большой проект. `localStorage` решает 80% проблем за минимальные усилия. Пользователь видит каталог, даже если API недоступен.

## A5. Состояния UI

**Options.**
- A. Два состояния: `loading` и `loaded`.
- B. Четыре состояния: `loading` (первый запрос), `retrying` (запрос идёт повторно), `fallback` (показываем кеш), `failed` (нет данных, ошибка).

**Decision.** Вариант B.

**Rationale.** Прозрачность для пользователя. Состояние `retrying` сигнализирует «не виси, идёт повтор». `fallback` показывает баннер «возможно неактуально». `failed` даёт кнопку «Повторить».

## A6. Тип ошибки

**Options.**
- A. Бросаем стандартный `Error`, в `message` — текст из API.
- B. Класс `ApiError extends Error` с полями `type`, `status`, `endpoint`, `attempt`. `type` — перечисление `ErrorType` (`NETWORK`, `TIMEOUT`, `RATE_LIMIT`, `SERVER`, `CLIENT`, `INVALID_RESPONSE`).

**Decision.** Вариант B.

**Rationale.** Одна точка маппинга API-ошибок в доменные типы. интерфейс и логика повторов смотрят на `error.type`, а не парсят `message`. Логирование получает структурированные данные.

## A7. Адаптер

**Options.**
- A. Использовать API-формат напрямую в компонентах. `item_id`, `item_name` и т.п.
- B. Адаптер `adaptProduct(raw)` преобразует в доменную модель `{ id, name, price, ... }`.

**Decision.** Вариант B.

**Rationale.** Изоляция формата поставщика. Если поставщик поменяет имена полей — правится только адаптер. Компоненты используют стабильную доменную модель.

## A8. Поиск: сервер vs клиент

**Options.**
- A. Серверный поиск: параметр `q` в `GET /products`, фильтрация на стороне поставщика.
- B. Клиентский поиск по уже загруженным (и адаптированным) товарам.

**Decision.** Вариант B.

**Rationale.** Контракт явно относит поиск по названию к клиенту. Серверного full-text нет; каталог небольшой. Клиентский фильтр не требует нового эндпоинта и не ломает retry/кеш API-слоя.

## A9. Слой ответственности поиска

**Options.**
- A. Вся логика в `CatalogPage`: debounce, фильтр, подсветка, история.
- B. Разделение: чистые утилиты + UI-компонент строки поиска на `CatalogPage`; отдельного маршрута/страницы поиска нет.

**Decision.** Вариант B.

**Rationale.** Тот же подход, что у фильтров (`filterProducts` + `CatalogFilters`). Поиск — строка над каталогом на той же странице, не отдельный экран. Утилиты покрываются юнит-тестами без React; `CatalogSearch` отвечает за ввод, историю и доступность; empty state списка остаётся в `CatalogPage`.

## A10. Debounce

**Options.**
- A. Без debounce: фильтровать на каждый символ.
- B. Debounce ~300 мс на значение, по которому фильтруется список; инпут обновляется сразу.
- C. Debounce через внешнюю библиотеку.

**Decision.** Вариант B. `SEARCH_DEBOUNCE_MS = 300`.

**Rationale.** Снимает гонку и лишние пересчёты при быстром вводе (R12). Инпут остаётся отзывчивым. Внешняя зависимость не нужна — достаточно `setTimeout` / хука `useDebouncedValue`. Предыдущий таймер сбрасывается; к списку применяется только актуальный query.

## A11. Состояние строки поиска: URL vs local state

**Options.**
- A. Только `useState` в `CatalogSearch` / `CatalogPage`.
- B. Синхронизация с URL через `useSearchParams`, параметр `q` (camelCase, как у фильтров).

**Decision.** Вариант B.

**Rationale.** Фильтры уже живут в URL; поиск в том же источнике даёт шаринг ссылки и восстановление после обновления страницы. В URL пишем debounce-значение (не каждый символ), чтобы не засорять history. История запросов в localStorage — отдельно от `q` и от `products_cache`.

## A12. Подсветка совпадений

**Options.**
- A. Собирать HTML-строку и вставлять через `dangerouslySetInnerHTML`.
- B. Безопасный split по совпадению и рендер через React (`<mark>` / фрагменты).

**Decision.** Вариант B. Матч по полю `name`, case-insensitive, после `trim`. Пустой query — без фильтра и без подсветки.

**Rationale.** Спецсимволы в запросе и имени товара не должны ломать разметку или открывать XSS (R13). Перед RegExp экранируем метасимволы. `description` в scope поиска не входит — только название, как в контракте.

## A13. История запросов в localStorage

**Options.**
- A. Без истории.
- B. Best-effort история в localStorage: лимит, дедуп, отдельный ключ.

**Decision.** Вариант B.

**Rationale.** Требование фичи. Ключ `SEARCH_HISTORY_KEY = "catalog_search_history"`, лимит `SEARCH_HISTORY_LIMIT = 8`, только нормализованные непустые строки, свежие сверху, без дублей. Пишем при «применённом» запросе (после debounce / выбор из истории), не на каждый символ. Чтение/запись в `try/catch`: при недоступном storage UI поиска работает без истории (R16, R17). Не смешивать с `CACHE_KEY`.

## A14. Пайплайн фильтрации и пустые состояния

**Options.**
- A. Один empty state на любой пустой список.
- B. Раздельные сообщения: пустой ответ API / фильтры vs пустой поиск; независимый сброс.

**Decision.** Вариант B. Порядок: `products → filterProducts → searchProducts → render`.

**Rationale.** Иначе пустой поиск путают с пустым каталогом или сбоем API (R14, R15, R6). Поиск без совпадений: «По запросу „…“ ничего не найдено» + «Очистить поиск». Пустые фильтры — прежнее сообщение и сброс фильтров. Сброс поиска не сбрасывает фильтры и наоборот.

## Структура файлов (итоговая)

```
src/api/
  catalog.js            # HTTP-клиент, retry, fallback на кеш
  catalog-adapter.js    # adaptProduct, adaptProductList
  errors.js             # ApiError, ErrorType, isRetryable
  mocks/
    catalog.json        # фикстура для VITE_USE_MOCK_DATA=true
  __tests__/
    catalog.test.js     # сценарии: happy path, таймаут, 5xx, fallback

src/utils/
  filters.js            # filterProducts (уже есть)
  search.js             # searchProducts, highlightMatches, нормализация query
  search-history.js     # read/write истории, лимит, дедуп
  __tests__/
    search.test.js
    search-history.test.js

src/hooks/
  useDebouncedValue.js  # debounce значения для фильтрации списка

src/features/catalog/
  CatalogSearch.jsx     # строка поиска + история над списком (не отдельная страница)
  CatalogSearch.module.css
  CatalogPage.jsx       # размещает CatalogSearch над каталогом; склейка фильтры → поиск → список / empty state
```

## Константы

- `API_BASE = "/api/v2"` в `catalog.js`
- `TIMEOUT_MS = 5000` (таймаут одного запроса)
- `MAX_RETRIES = 3`
- `CACHE_KEY = "products_cache"` (ключ localStorage)
- `SEARCH_DEBOUNCE_MS = 300`
- `SEARCH_HISTORY_KEY = "catalog_search_history"`
- `SEARCH_HISTORY_LIMIT = 8`
- query-параметр поиска в URL: `q`
