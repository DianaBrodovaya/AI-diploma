# Реестр рисков — интеграция API каталога

> Список того, что может пойти не так, и что мы делаем, чтобы не положить продакшен. Обновляется при обнаружении новых сценариев в продакшене.

Шкала вероятности: низкая (<5% запросов), средняя (5-20%), высокая (>20%).
Шкала последствий: мелкое (неудобство, не блокирует), серьёзное (раздел недоступен), критичное (продакшен недоступен).

| # | Риск | Вероятность | Последствия | Мера |
|---|---|---|---|---|
| R1 | Таймаут сети (упал канал, долгий отклик поставщика) | средняя | серьёзное (каталог пустой) | `AbortController` с таймаутом 5 с → повтор до 3 раз с нарастающей задержкой 1/2/4 с → фолбэк на кеш |
| R2 | 5xx от поставщика | средняя | серьёзное | Повтор как в R1 → фолбэк на кеш |
| R3 | 429 rate limit | низкая | мелкое (временное замедление) | Без автоповтора: под лимитом повторять вслепую нельзя. Сразу к фолбэку на кеш, `Retry-After` сохраняется в ошибке как подсказка |
| R4 | 401 невалидный ключ (утёк, поменяли) | низкая | критичное | Без повтора. Немедленное оповещение → ручной откат на моки |
| R5 | Невалидный JSON в ответе | низкая | серьёзное | `try/catch` вокруг `response.json()` → `ApiError(INVALID_RESPONSE)` → фолбэк на кеш |
| R6 | Пустой массив `items` при 200 | средняя (легитимный кейс) | мелкое | Считаем валидным ответом. Интерфейс показывает «Товары не найдены». Не путать с R5 |
| R7 | Изменение формата ответа поставщиком | низкая | критичное | Валидация структуры в адаптере. Если обязательное поле пропало — `INVALID_RESPONSE`, фолбэк на кеш, оповещение |
| R8 | Поставщик вернул HTML-страницу вместо JSON (cloudflare, maintenance) | низкая | серьёзное | Проверка `response.headers.get('content-type')` перед парсингом. Если не JSON — `INVALID_RESPONSE` |
| R9 | Кеш устарел на несколько часов/дней | средняя | мелкое | Интерфейс помечает данные как «возможно устарели». Метка времени сохраняется с кешем |
| R10 | Режим моков включён в продакшене по ошибке | низкая | критичное (показываем фиктивные товары) | Флаг `VITE_USE_MOCK_DATA` — только в окружении разработки. CI проверяет, что в сборке для продакшена переменная не `"true"` |
| R11 | LocalStorage недоступен (приватный режим Safari, квота переполнена) | низкая | мелкое | Фолбэк на memory-cache внутри модуля. Это даёт хотя бы одну сессию, хоть и не переживёт перезагрузку |
| R12 | Гонка при быстром вводе в поиск: debounce ещё не сработал / предыдущий запрос «догоняет» позже | средняя | мелкое (мигание списка, неверный набор) | Debounce на клиенте (типично 300 мс). Применять фильтр только по актуальному значению строки; игнорировать устаревшие колбэки таймера (сброс предыдущего `setTimeout` / проверка версии запроса) |
| R13 | Подсветка совпадений ломает разметку или даёт XSS (спецсимволы в запросе / имени товара, `dangerouslySetInnerHTML`) | средняя | серьёзное | Не строить HTML из сырого запроса. Экранировать текст товара; подсветку делать через безопасный split/`<mark>` в React или экранированный шаблон. Спецсимволы RegExp (`*`, `(`, `[` и т.п.) экранировать перед матчингом |
| R14 | Пустой результат поиска путают с пустым каталогом / сбоем API (R6) | средняя | мелкое | Отдельное пустое состояние поиска: «По запросу „…“ ничего не найдено» + сброс строки поиска. Не подменять сообщениями R6 («Товары не найдены» при пустом `items`) и `failed` |
| R15 | Поиск + фильтры дают пустой список, пользователь не понимает причину | средняя | мелкое | Пустое состояние учитывает активный поиск и фильтры; сброс поиска не сбрасывает фильтры (и наоборот), либо явные отдельные действия «Очистить поиск» / «Сбросить фильтры» |
| R16 | История запросов в localStorage недоступна или квота переполнена | низкая | мелкое | `try/catch` вокруг чтения/записи. Без истории UI поиска работает; история — best-effort. Не падать и не блокировать ввод |
| R17 | История запросов разрастается без лимита (квота, шум в UI) | средняя | мелкое | Ограничить длину (например, последние 5–10 уникальных запросов), дедупликация, хранить только нормализованные непустые строки |
| R18 | Поиск работает только по уже загруженной странице товаров, а не по всему каталогу поставщика | высокая (по дизайну) | мелкое | Ожидаемо: поиск клиентский (см. контракт). Не обещать серверный full-text. При пагинации API — явно ограничить scope «по загруженным товарам» |

## Сценарии, которые мы принимаем как неизбежные

- Мы не можем обнаружить, что поставщик вернул неверные *значения* при правильной структуре (например, не ту цену). Это требует кросс-валидации с другим источником и не входит в scope этой интеграции.
- Мы не гарантируем транзакционную консистентность между каталогом и корзиной (товар может пропасть из каталога после добавления в корзину). Это обрабатывается на шаге checkout.
- Поиск по названию выполняется на клиенте по уже загруженным товарам; полнотекстовый поиск на стороне поставщика в scope не входит.
- История поисковых запросов локальна для браузера пользователя и не синхронизируется между устройствами.
